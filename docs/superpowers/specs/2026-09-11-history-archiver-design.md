# Server-side location history archiver

## Motivation

Today, macless-haystack's endpoint (`endpoint/mh_endpoint.py`) has no memory of its own. Every time the frontend app asks for a device's location history, `do_POST` calls Apple's `https://gateway.icloud.com/acsnservice/fetch` live and returns whatever Apple currently has on file — nothing is persisted server-side.

The app builds its own local history by fetching on app-open (and on manual per-item refresh) and merging into `flutter_secure_storage`. That means:

- History only grows when the app is actually opened.
- Apple's own server-side report retention is limited (the code's default query window is 7 days), so any gap longer than that between app opens is permanently unrecoverable — nothing local or remote ever archived it.
- Every app-triggered fetch is a live call to Apple, with no caching, which is wasteful and (per this month's GSA 503 incident, see `sina/fix_gsa_client_info_503`) something to be conservative about — Apple has shown it will block clients it doesn't like the shape of.

Goal: let location history accumulate independent of whether any client app is ever opened, and reduce how often the server has to call Apple at all.

## Non-goals

- No changes to the Flutter/web frontend in this iteration. The existing `do_POST` response shape is preserved exactly, so the app needs zero code changes to benefit from deeper history.
- No decryption of location payloads server-side. The server continues to store and forward encrypted blobs exactly as Apple returns them; decryption stays client-side (`decrypt_reports.dart`), so tracker private keys never need to be exposed to more code than necessary and a server compromise doesn't expose plaintext locations.
- No UI for wiring the app's existing "Refresh" swipe action to the new `force` request flag — that's a small, separate follow-up once this backend piece exists.

## Architecture

New module: `endpoint/history/archiver.py`

- `derive_hashed_public_key(private_key_b64) -> str` — the same EC derivation `generate_keys.py` already performs (P-224 private key → public key point → SHA256 → base64) to compute the "id" Apple's fetch API expects, given only a private key. Ported, not reinvented.
- `load_tracked_keys(devices_file_path) -> list[str]` — parses a `PREFIX_devices.json`-shaped file (the exact format `generate_keys.py` produces and the app already imports — see `generate_keys.py`'s `TEMPLATE`: `id`, `name`, `privateKey`, `additionalKeys`, etc.) and returns the full flat list of hashed public keys (main `privateKey` plus every entry in `additionalKeys`, each hashed).
- `HistoryStore` — a thin wrapper around SQLite (`endpoint/data/history.db`):
  - `record_reports(hashed_key, reports)` — insert, deduped by `(hashed_key, timestamp)`.
  - `get_reports(hashed_keys, since) -> list[dict]` — read back stored entries no older than `since`. `do_POST` already computes a `startdate` cutoff from the request's `days` field to filter Apple's live results (existing code, unchanged); this same cutoff is passed straight through here so archived and live results are windowed identically. Not a new filtering behavior, just applying the existing one to both sources.
  - `mark_polled(hashed_key)` / `last_polled_at(hashed_key) -> int | None` — tracks *when we last successfully asked Apple* for this key, independent of whether that poll found any new reports.
- `run_archiver_loop(interval_hours)` — background job: load tracked keys, and every `interval_hours`, fetch from Apple (reusing the same auth/anisette path `do_POST` already uses) for all tracked keys, store new reports, mark each as freshly polled, sleep, repeat. Runs as a daemon thread started from `mh_endpoint.py`'s startup, not a separate process — one process per container, consistent with the Dockerfile cleanup in `sina/dockerfile-copy-build`, and it reuses the auth machinery already imported in that process.

## Data flow

**Setup:** the user copies their existing `PREFIX_devices.json` (already generated by `generate_keys.py`, already imported into the app) into `endpoint/data/devices.json`. If this file isn't present, the archiver thread never starts and `do_POST` behaves exactly as it does today — the feature is entirely opt-in with zero risk of regression for anyone who doesn't set it up.

**Background polling:** every `history_poll_interval_hours` (config, default 4), for each tracked hashed key: fetch from Apple, insert any report not already in `HistoryStore` (deduped by `(hashed_key, timestamp)`), mark the key as freshly polled.

**Serving a request (`do_POST`):** for each requested `id` (hashed key) in the request body:
1. Check `last_polled_at(id)`.
2. If it's within `history_poll_interval_hours` of now, **and** the request body doesn't have `"force": true` → skip Apple entirely, read from `HistoryStore`.
3. Otherwise (stale, or `force: true`) → call Apple live, `record_reports` + `mark_polled` on success, then read from `HistoryStore` (which now includes what was just fetched).
4. If the live call fails in step 3, log a warning and fall back to serving whatever's already in `HistoryStore` rather than failing the request — stale data beats an error.

Either way, the response is built by reading from `HistoryStore` after any necessary refresh, sorted by timestamp, in the exact same shape `do_POST` returns today (each stored row keeps the *entire* raw Apple entry, not just the payload, since the app's Dart decrypt path reads more than just `payload` off each entry).

## Config

New optional keys under `[Settings]` in `config.ini` (all optional; absent `history_devices_file` on disk = feature off):

| Key | Default | Purpose |
|---|---|---|
| `history_devices_file` | `devices.json` | Filename under `data/` to read tracked keys from |
| `history_poll_interval_hours` | `4` | Both the background poll cadence and the on-demand freshness window (one knob, not two, to keep config surface small) |

## Error handling

- Missing/malformed `devices.json` → log once at startup, archiver thread doesn't start, `do_POST` unaffected (today's live-only behavior).
- Apple fetch fails during a scheduled poll → log, skip this cycle, retry next interval. Never crashes the thread.
- Apple fetch fails during an on-demand refresh (stale or forced) → fall back to cached data with a logged warning, per the data-flow section above.
- `HistoryStore` errors (disk full, corruption, etc.) → logged, request degrades to calling Apple live directly without caching, rather than crashing the server.

## Testing

Extends the existing `endpoint/tests/` pattern (pytest, stdlib only — `sqlite3` needs no new dependency):

- `derive_hashed_public_key`: verify it's internally consistent (deterministic for a given private key, changes when the key changes) and matches manual recomputation of `SHA256(public_key_bytes)` → base64 for a generated test keypair.
- `HistoryStore`: insert/dedup/read against an in-memory (`:memory:`) SQLite database — covers duplicate inserts collapsing to one row, `last_polled_at` tracking, and reads returning the full stored entry unmodified.
- `do_POST`'s cache/freshness/force decision logic: mocked `HistoryStore` and mocked Apple fetch, covering: fresh cache → no Apple call; stale cache → Apple called and result stored; `force: true` → Apple called regardless of freshness; Apple failure during a needed refresh → falls back to cached data instead of erroring.
- The archiver loop's single-iteration logic (parse devices file → derive keys → fetch → store) tested in isolation with mocks; the outer sleep/repeat wrapper is trivial and not separately tested, matching how the GSA 2FA work didn't test the outer network retry loop itself.

## Follow-ups (explicitly out of scope here)

- Wiring the app's existing per-item "Refresh" action to send `force: true`, so a manual refresh in the UI means something again instead of always serving cache.
- Pruning old rows from `history.db` (currently grows unbounded — acceptable for now given SQLite's low overhead per row, but worth a config-driven retention limit later if it matters).
